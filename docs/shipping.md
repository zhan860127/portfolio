# 寄貨單（7-ELEVEN 貨到付款）

客人把自己已確認訂金的訂單勾成一張單、填好收件資訊，直接送進後台。
運費固定 80 元，取貨時以貨到付款支付尾款。

---

## 1. 為什麼不走聊天室

原本的構想是「按一個按鈕把寄貨單送進與清嶼的聊天室」。查證之後放棄了，
理由依序是：

1. **Instagram 私訊沒辦法帶文字進去。** Meta 文件裡 `ig.me/m/{username}` 唯一支援的
   額外參數是 `ref`，而且只收英數與 `-` `_` `=`，中文寄貨單塞不進去；
   ig.me 連結在 IG 網頁版也不支援。做得出來的只有「先複製、再開 DM、客人自己貼上」。
2. **聊天室會漏接。** 就算改用 LINE 官方帳號（它的 `oaMessage` URL 確實可以預填文字），
   預填也只是把字放進輸入框 —— 客人還要自己按送出。按了沒送、送了你沒看到，
   這兩種情況在聊天室裡都沒有任何痕跡，而寄貨資訊漏接的代價是包裹寄錯人。
3. **沒有紀錄就沒辦法改。** 客人電話打錯一碼這件事一定會發生。資料只存在聊天室時，
   你只能往上翻，而翻到的可能是三天前那一版。

所以改成**直接送進後台**：客人送出就進資料庫，後台有一頁可以看，
客人自己也能回來修改或取消。

> LINE 預填那條路並沒有被證明不可行，只是被「聊天室不適合當單據的保存地點」否決。
> 之後若要加「順手也傳一份到 LINE」當輔助通知，隨時可以加上去。

## 2. 資料庫

Migration：`server/database/migrations/0002_shipping_requests.sql`（純新增）。

| 動作 | 內容 |
|---|---|
| 新增 enum | `shipping_status`：`pending` / `shipped` / `cancelled` |
| 新增表 | `shipping_requests` |
| 既有表新增欄位 | `market_orders.shipping_request_id`（可為 NULL） |

### 2.1 一張寄貨單 = 一個包裹

市集是「一單一件」，所以客人買三件就是三筆訂單。不合併的話運費要收三次。
`shipping_requests` 因此是一對多：一張單收多筆 `market_orders`。

### 2.2 為什麼用欄位而不是中介表

`market_orders.shipping_request_id` 直接保證「一筆訂單最多只出現在一張寄貨單上」——
這是欄位本身的性質，不需要再補一個唯一索引去擋。
中介表則要額外處理「取消過的單子不該卡住訂單」這種 partial unique index 的細節。

取消寄貨單時這個欄位會回到 NULL，訂單就能重新併進新的一張。

### 2.3 兩個不變量

```sql
-- 一位客人同時只能有一張「待出貨」的寄貨單
CREATE UNIQUE INDEX shipping_requests_one_pending_per_user_idx
  ON shipping_requests (user_id) WHERE status = 'pending';
```

沒有這條的話，重複點送出會產生兩張內容幾乎一樣的單子，而你在後台沒辦法判斷該寄哪一張。
有了它，「送出」與「改地址」在客人眼裡就是同一個動作，API 也因此做成 upsert
而不是 POST／PATCH 兩個端點。

另一個不變量是上面的 `shipping_request_id` 欄位本身。
掛訂單時用的是條件式 UPDATE：

```sql
UPDATE market_orders SET shipping_request_id = $1
WHERE id = ANY($2) AND user_id = $3 AND shipping_request_id IS NULL
```

併發時搶輸的那邊 affected rows 會少，handler 對不起來就整筆 rollback，
不會出現兩張單寄同一件作品。跟下單搶保留權是同一招。

### 2.4 金額一律快照

`item_total_cents` / `deposit_paid_cents` / `shipping_cents` / `cod_cents` 與
`items`（jsonb）都是成立當下的快照。運費或商品價格日後調整，都不該改變已經送出的單子 ——
客人看到的「貨到付款應付」必須跟當初送出時一模一樣。

`items` 同時也是取消後唯一的歷史：訂單的連結被清回 NULL 之後，
這張單寄過什麼就只剩這份快照查得到。

## 3. 金額怎麼算

```
貨到付款應付 = 作品金額合計 − 已付訂金 + 運費
```

- **運費固定 80 元，一張單收一次**，不是每件各收一次（一張單就是一個包裹）。
- 訂金是下單時就付掉的，取貨時只收尾款；少扣這一段客人會被收兩次訂金。
- 訂金萬一被設定得比售價還高，尾款取 0，但運費仍然要收。

數字的唯一事實來源在 `server/utils/shipping.ts` 的 `SHIPPING_FEE_CENTS`
與 `summarizeShipment()`。前端只顯示 API 回傳的運費，**不寫死 80**，
否則哪天調整運費會變成兩邊不一致（有測試鎖住這點）。

---

## 4. 哪些訂單可以併單

`deposit_confirmed`（已確認訂金）與 `completed`（已完成），而且還沒被任何寄貨單收走。

收 `completed` 是刻意的：後台的「確認售出」有可能先按了，
你的帳務動作不該害客人填不了寄貨單。

## 5. 流程

```
客人                                        清嶼
──────────────────────────────────────────────────────────
下單 → 匯訂金 → 填末五碼
                              後台確認訂金入帳
「我的市集 → 寄貨單」
勾選要一起寄的作品
填姓名／手機／7-11 門市
送出                     ──────▶  後台「寄貨單」看到這張單
                                  複製收件資訊 → 貼進 7-11 出貨系統
                                  標記「已寄出」
客人在超商取貨、付尾款
```

`/me` 的「已確認訂金」區塊有一顆「去填寄貨單」直接跳到那一頁 ——
不然客人不會知道有這個分頁。

## 6. 幾個刻意的決定

| 決定 | 理由 |
|---|---|
| 手機只收 09 開頭的十碼 | 超商取貨通知是簡訊，填市話的包裹客人收不到通知。輸入時的 `-`、空白與 `+886` 會自動正規化 |
| 門市店號可以不填 | 客人不一定查得到；門市名稱才是必填 |
| 「標記已寄出」不順手把訂單改成已完成 | 「包裹寄出」與「這筆交易結案」是兩個不同的人工確認時點，跟訂金／售出分兩步同一個理由 |
| 已寄出之後不給改、也沒有回頭路 | 包裹已經在超商了。要改就重開一張並在備註寫明原因，而不是把紀錄改掉 |
| 後台每張單都有「複製收件資訊」 | 手動重打姓名電話門市，是整個流程裡最容易出錯、錯了最難補救的一步 |
| 一張單最多 20 筆訂單 | 再多就該拆成兩個包裹 |

## 7. 還沒做 / 要注意

1. **本機已經跑過，Vercel 還沒。**
   `pnpm run db:migrate` 套用在開發用的 Postgres 容器（`127.0.0.1:55432/market`），
   並驗證過表、16 個欄位、partial unique index 與 `shipping_status` enum 都在。

   `.env` 的連線字串指的是本機容器、不是 Neon（見 online-market.md §7.5），
   所以**正式環境那一份要另外跑**：Vercel 上的 Neon 連線字串只存在那邊的環境變數裡。
   跑之前先看 §10.9 —— preview 與 production 目前共用同一個 Neon 資料庫。
   內容是純新增（一個 enum、一張表、一個可為 NULL 的欄位），不會動到既有資料。
2. **沒有從瀏覽器端到端跑過。** 填寄貨單需要 Google 登入（那是你的帳號），
   跟 §10.5 一樣的限制。已驗證的是：

   | 層 | 內容 |
   |---|---|
   | 規則層 | 20 個測試：金額公式、手機正規化、可併單條件、狀態轉換 |
   | 元件層 | 9 個測試：勾選、即時試算、送出的 body、擋錯、已寄出不給改 |
   | 資料庫層 | 7 個測試（真實 Postgres）：一人一張待出貨單、訂單不被搶走、取消後可重新併單、刪單不會刪掉訂單、金額快照 |
   | 路由 | 五個端點都回 401 而不是 500 |

   建議你自己登入後走一遍：填寄貨單 → 後台看到 → 標記已寄出。
3. **沒有任何通知。** 客人送出後你不會收到提醒，要自己進後台看；
   後台標記已寄出，客人也不會收到通知。專案目前完全沒有郵件或推播基礎建設
   （§10.1 已記錄同樣的限制）。
4. **運費是寫死在程式裡的常數**，不是後台設定。要改得改 `SHIPPING_FEE_CENTS`
   並重新部署。做成活動層級的設定不難，但在只有一個運費級距之前是多餘的複雜度。
5. **7-ELEVEN 的貨到付款單仍然要你在 7-11 的系統（ibon／賣貨便）開。**
   這裡收的是「要輸入進那個系統的資料」，不是物流單號；
   系統也不會知道包裹實際到店沒有。
